# 10. 方案：sidebar-app 宿主与 Tauri 层通讯

> **状态：提案（未实施）**。本文档描述旧架构下的设计方案。  
> **当前实现**：核心基础设施已重构为 `packages/dsh-tauri`（替代已废弃的 `archive/dsh-tauri`），  
> 采用五协议体系（defineRoutes / defineRegister / defineAdapter / storage / valtio-define）。  
> 当前实现请参阅 `docs/plugins/dsh-tauri-设计重构迁移.md` 与 `docs/plugins/dsh-tauri-路由依赖注入.md`。
>
> 动机来自两个问题——
> 1. 「为什么我们不在 host 层做数据的传输？」——以 `dsh-tauri-pet`（客户端轮询快照转发）为反例。
> 2. `source/dsh-dafeiyu` 是怎么做的？（宿主订阅跨端口 `session/event` 事件轴）。
>
> 本文回答「哪一层该做数据传输、为什么」，并给出 sidebar-app（`dsh-tauri-panel`）跨 host↔Tauri
> 边界的通讯方案。`dsh-dafeiyu` 是 `source/` 下的独立仓库（非本 workspace 包），仅作架构参照，
> **不作为可直接复用的实现**。

## 1. 结论先行

- **宿主层确实更适合做「数据」传输**：host 半区原生拥有 `ctx.on('session/event')` 语义事件轴（细粒度
  `turn/start`、`assistant/chunk`、`tool/call`、`turn/end`…），天然是增量、去重后的最小载荷；而客户端
  半区**只有快照 API**（`ctx.sessions.list.getSnapshot()`），拿到的是一整棵 byId 快照树，必须自己 diff。
  这正是 #396 前端延迟的根因——差值算子的反复全量重投影。
- **但「宿主层数据传输」缺的是一段 host→client 的推送桥**。当前 host 只能把数据通过 `invoke` 桥
  （request/reply、按 nonce 匹配）回给对方，**没有一个面向客户端的实时事件推送通道**。
- **sidebar-app 的推荐做法 = 宿主轴订阅 + 桥式重放成客户端协议服务**，而不是让客户端继续差值快照。
  落到本仓库「退级阶梯」（`docs/AGENTS.plugins.md`）上即：用官方公开 API（`session/event`）打底，
  只缺的推送通道用「桌面壳补丁」补（比 DOM 补丁 / 禁用好）。

## 2. 三层模型（先分清「层」）

| 层 | 代码位置 | 运行环境 | 能拿到的数据 |
| --- | --- | --- | --- |
| **Client half**（browser） | `packages/<pkg>/src/client/` | Tauri webview 内 iframe | 快照 API：`ctx.sessions` / `ctx.workspaces`（类型为 `unknown`，消费方自行断言）；`ctx.slots` / `ctx.reflect` / `ctx.layout` / `ctx.locale` |
| **Host half**（Node） | `packages/<pkg>/src/host/` | 桌面壳 Node 运行时 | `ctx.sessions`(SessionStore) / `ctx.workspaceRegistry` / `ctx.webServer` / `ctx.tools` / `ctx.agents` / `ctx.llm`；**外加 cordis 事件轴 `ctx.on(...)`** |
| **Tauri（Rust 壳）** | `src-tauri/src/` | Rust | `invoke` command；桌面壳**补丁**（`src-tauri/src/service/workflow/*_patch.rs`）在启动前对捆绑核心打补丁暴露窄面能力 |

**客户端上下文**（旧路径 `archive/dsh-tauri/src/client/types/context.ts`，现已迁移到新协议）：

```ts
export interface ClientContext {
  locale: LocaleService
  layout: ILayout
  slots: ClientSlots
  reflect: ClientReflect
  effect: ClientEffect
  sessions?: unknown   // 宿主服务，消费方自行断言领域类型（快照式）
  workspaces?: unknown
}
```

注意：**`ClientContext` 里没有 `.on()` / 事件订阅**。客户端拿不到事件轴，只有 `sessions`（快照）与
`reflect`（反射服务）。这是「客户端只能凑快照」的结构性原因。

**宿主上下文**（旧路径 `archive/dsh-tauri/src/host/types/index.ts`，现为 `packages/dsh-tauri/src/host/types/index.ts`）
是 `Context & { agents, sessions, workspaceRegistry, tools, webServer, connection?, llm?, ... }`，
`Context` 来自 `@deepseek-ai/cordis`，内含事件发射/订阅能力。

## 3. 现有通讯渠道盘点

| # | 渠道 | 方向 | 形态 | 数据 | 代码锚点 |
| --- | --- | --- | --- | --- | --- |
| ① | **host 事件轴** `ctx.on('session/event', fn, {global:true})` | 端内（host→host） | 细粒度语义事件流 | `turn/start` `step/start` `assistant/chunk` `tool/call` `tool/result` `user/message` `turn/end` `approval/asked` `approval/decided` `todo/write` | `dsh-dafeiyu/src/plugin.js:238`；`dsh-tauri-worktree/src/host/apply.ts` `ctx.on('session/event', ...)` |
| ② | **invoke 桥** `invokeBridgedTauri(cmd, args)` | client→host (Tauri) | request/reply，按 nonce 匹配，`INVOKE_TIMEOUT_MS` 超时 | 一次性 command 调用/返回值 | `packages/dsh-tauri/src/client/service/invoke.ts`（旧 `archive/dsh-tauri`，现统一走新协议）；宿主监听 `src/hooks/use-iframe-invoke.ts` |
| ③ | **host 事件轴 → invoke 桥 reply** | host→client | reply 形态（非事件） | 仅回 request 对应的 value/error | `src/hooks/use-iframe-invoke.ts` `iframeRef.current?.contentWindow?.postMessage({source:'dsh-desktop-invoke', type:'dsh://tauri:reply', nonce, ...})` |
| ④ | **webServer HTTP** `ctx.webServer.register(route)` | host 对外 | REST / JSON | 宿主能力 HTTP 暴露；客户端 `ofetch` 走 **pull** | `packages/dsh-tauri/src/host/types/index.ts`（`WebServerService`）；客户端请求经 `packages/dsh-tauri/src/client/request/index.ts` 统一走新协议 |
| ⑤ | **reflect 协议** `ctx.reflect.provide/get(key)` | 客户端端内 | 同步服务注册/取用 | 面板能力协议（`panel.protocol`） | `packages/dsh-tauri-panel/src/client/register/panel-service.ts`；`PROTOCOL.md` |

**关键缺口**：渠道 ③ 是唯一 host→client 的 postMessage 通道，但它是 **reply 形态**——核心是
「按 nonce 回一次」。没有「宿主主动、多次、持续推送事件」的通道。要做宿主层数据传输的实时推送，
需要把它泛化成一个事件通道（见 §6 方案 A）。

## 4. `dsh-tauri-pet` 与 `dsh-dafeiyu` 的本质差异

差异不在「代码质量」，而在**渲染者所在的层**：

| | `dsh-tauri-pet` | `dsh-dafeiyu` |
| --- | --- | --- |
| 渲染者 | 桌面 webview 里的气泡（**client half**） | 宿主驱动的 Python 子进程（**host half**） |
| 数据来源 | `ctx.sessions` **快照 API**（byId 整棵树） | `ctx.on('session/event')` **增量事件轴** |
| 数据形态 | 全量快照 → 需自己 diff | 细粒度语义增量 → 已去重的最小载荷 |
| 传输 | `pushPetSession` → `invokeBridgedTauri` → Tauri command → 气泡侧状态 | `bridge.send(message)` → **JSON over stdio** 到 Python helper |
| 性能模型 | 差值算子的「无变化重投影」易爆炸（#396） | 事件驱动，只在事件发生时通知 |

- `dsh-tauri-pet`：`registerPetSessionForwarder` 在客户端轮询 `sessions.list.getSnapshot()` + 逐会话
  `emitIfChanged` → 剩余 #396 根因就是它的差值投影（每 tick 重建 byId 导致 lastInput 引用恒变，
  `sameRefs`/`lastProjected`/`skipRef`/`dirty-gate`/`membership-dedup` 均为这一脆弱树上的加固）。
- `dsh-dafeiyu`：宿主订阅事件→`companion-reducer`（`switch` 归约成 `CompanionMessage`，再 `#signature`
  渲染去重）→ 经 stdio 推给 Python helper。它不需要快照 diff，因为事件本身就是增量。

## 5. 为什么「宿主层做数据传输」是可行的正解（但需要一座桥）

**宿主层做数据传输的好处**（相对于客户端快照 diff）：

1. **载荷最小**：事件即增量，不需要客户端拿到整棵 byId 再逐字段比较。
2. **源头权威**：`session/event` 由 dsh 核心在业务状态落定后发射（`turn/end` 等），没有「我 diff 出来的
   假变化」。
3. **单一写入、多点消费**：同一宿主轴可被 sidebar / pet / 任何宿主插件消费，天然去重。

**但宿主层的数据要到达渲染者（浏览器）**，必须过一段 host→client 通道。现状只有 reply 形态的
postMessage（渠道③）与 pull 形态的 HTTP（渠道④）。这决定了 sidebar-app 走不到「纯宿主事件轴」
——除非我们补桥。

## 6. 推荐方案

### 方案 A（推荐）：宿主事件轴 → 桥式重放 → 客户端协议服务

让 **host half 订阅 `session/event` 事件轴**，归约+去重后，通过一条**新的 host→iframe 事件通道**
推送给客户端；客户端经 `ctx.reflect.provide('…', api)` 暴露给 UI（`dsh-tauri-panel` 及兄弟插件消费）。

```
[host half]  dsh 核心 --session/event--> 宿主订阅器(归约/去重)
                          |
                          v  host→iframe postMessage 事件通道（新增）
[client half]  协议服务 ctx.reflect.provide('sidebar.sessions', api)
                          |
                          v
              dsh-tauri-panel / 其它客户端插件 UI
```

要点（全部对齐现有模式，不发明新框架）：

1. **宿主订阅器用官方公开 API**：`ctx.on('session/event', ...)` —— 当前 `dsh-tauri-worktree` 已在
   `host/apply.ts` 这么用了，宿主插件（`dsh-dafeiyu`）也用 `{global:true}`。不必打补丁。
2. **归约逻辑参照 `dsh-dafeiyu` 的 `companion-reducer` 模式**：switch 语义事件 → 紧凑投影；用
   rendered-signature（`#signature`）去重，避免无变化重发。这部分是可移植的纯函数。
3. **唯一需要补的是「事件通道」**：这是官方公开 API 未提供的，按退级阶梯第 2 级「桌面壳补丁」补。
   形态复用渠道③的 postMessage，但换一个独立 `source`/`type`（如
   `source:'dsh-desktop-delta', type:'dsh://session:delta'`），并镜像一个客户端接收端
   （`packages/dsh-tauri` 内，采用新协议的 `defineRegister` / `defineAdapter` 标准化注册）。
   宿主侧同样要做 `event.source` + `origin` 双重校验（`use-iframe-invoke.ts` 同款），
   且**只对可信 DSH iframe 推送**。
4. **客户端暴露面做成「可选能力」**：与 `panel.protocol` 的可选方法约定对齐
   （`setPanelWidth?`、`openDetails?`，见 `PROTOCOL.md`），消费方一律
   `get('sidebar.sessions')?.subscribe?.(...)` 探测调用，老版本对象缺字段时降级。

### 方案 B（兜底/轻量需求）：客户端快照 + 收紧的差值（pet 现状，已硬化）

若 sidebar-app 只需要少量状态（比如「会话是否在 run」），不值得为它补一条事件通道：
让客户端订阅快照但**只在真正需要的字段变化时重渲染**。`dsh-tauri-pet` 已把这一硬化做完了
（`sameRefs` 引用相等短路、`lastProjected` 缓存、`skipRef`/`dirty-gate`/`membership-dedup`），
可以直接复用其模式，但要注意它仍是被动轮询——会话量一大或 byId 高频重建时仍有余热。

### 建议

- **新增功能/高频率**（sidebar 显示实时会话状态、活动、进度）→ **方案 A**，把数据传输收敛到宿主层，
  避免把「每次全量快照的差值」成本摊到浏览器。
- **纯 UI 组合、低频**（action item 展示、宽度协议）→ 维持现状（`panel.protocol` / CSS 变量），不需要事件轴。

## 7. 与 `panel.protocol` 的集成（可选扩展）

`panel.protocol` 已是「reflect.provide/get + 可选能力探测」的范本
（`packages/dsh-tauri-panel/src/client/register/panel-service.ts`，`PROTOCOL.md`）。宿主层事件重放
可追加为 `panel.protocol` 之上/旁路的**另一个反射服务**，保持二者解耦：

```ts
// 新协议：sidebar.sessions（可选能力，宿主层数据重放）
export interface SidebarSessionDeltaProtocol {
  /** 订阅宿主层归约后的会话语义增量；返回取消订阅的 disposer。 */
  subscribe?: (listener: (delta: SessionDelta) => void) => () => void
  /** 一次性取当前快照（回退/初始化用，对应方案 B）。 */
  getSnapshot?: () => SessionListSnapshot
}
// 消费方：服务缺失（老核心/宿主未装）时降级，绝不白屏。
const delta = ctx.reflect.get('sidebar.sessions') as SidebarSessionDeltaProtocol | undefined
const off = delta?.subscribe?.(onDelta)
return () => off?.()
```

能力矩阵：

| 消费方 | 方案 | 说明 |
| --- | --- | --- |
| `dsh-tauri-panel` 内嵌第三方功能面板 | A | 实时会话状态、活动流 |
| 空会话/低频 UI | B | 快照 + 收紧差值 |
| 宽度/详情列 | 现状 | `setPanelWidth?` / `openDetails?` 可选能力 |

| 阶梯 | 本场使用 |
| --- | --- |
| 1. 官方公开 API | `ctx.on('session/event')`（宿主订阅）；客户端 `ctx.reflect.provide/get` |

## 9. 落地边界与注意事项

- **`dsh-dafeiyu` 不是本 workspace 包**（在 `source/`），不能直接 `import`；只取它的「事件轴归约 +
  signature 去重」设计思路，代码需按本仓库规范重写（`docs/AGENTS.plugins.md` 目录/依赖/类型规范）。
- **客户端依赖收敛**：新增宿主通道的客户端接收端应落在 `packages/dsh-tauri` 内（它是唯一内联
  `unstorage`/`hookable`/`ofetch` 的 client bundle，通过新协议导出），其余插件从 `dsh-tauri/client` 导入，不重复内联。
- **白名单/越权**：宿主侧对事件通道同样要做 `event.source` + `origin` 双重校验与**可信插件**清单，
  与 `ALLOWED_INVOKE_CMDS`（`src/hooks/use-iframe-invoke.ts:37`）同一套思路。
- **先探测后调用**：所有新增协议字段做成可选（`?`），消费方 `?.()` 探测缺字段即降级。
- **测试面**：归约纯函数（事件→投影→signature 去重）单测；channel 的收发/越权/超时用
  `vitest` 覆盖；宿主订阅按 `session-tests` 惯例写。

## 11. 实施状态（dsh-tauri-pet 方案 1：host → rust → pet webview）

> 用户选定「方案 1」（= 本提案的宿主层数据传输精神），把 `dsh-tauri-pet` 的会话转发从
> 「客户端 poll 快照差分（#396 根因）」搬为「宿主增量轴 → Rust SSE 消费 → `emit_to('pet')`」。
> 与 §6 方案 A 的差异：pet 是顶层 Tauri webview（自带 Tauri internals），**不需要** host→iframe
> postMessage 桥，Rust 直接 `emit_to` 即可；故这条链更短。

### 实现的链（三层，均带验证）

```
[dsh core] --session/event--> [host half: packages/dsh-tauri-pet/src/index.ts]
                                (SessionStore 总线; peerOf 适配; reducer 投影去重)
                                  |
                                  v  ctx.webServer.register GET /api/dsh-pet/session-stream (SSE)
[Rust]  spawn_pet_session_stream (src-tauri/src/bridge/pet.rs)
            reqwest SSE 消费 http://127.0.0.1:<port>/api/dsh-pet/session-stream
            data: {"action":...,"payload":...}  → emit_to(pet_window, "session:create|update|remove", payload)
                                  |
                                  v
[pet webview]  src/pet/hooks/use-bubble.ts  listen('session:create/update/remove')
```

  累计态 + lastSent 去重）+ `host/reducer.test.ts`（9 用例）。
