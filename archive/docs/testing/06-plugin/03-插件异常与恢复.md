## [P1] 验证补丁层 YAML 语法错误可被显式隔离并恢复启动

[测试类型] 可靠性
[前置条件] 已装入 dsh 内核可运行；`$DSH_HOME`（release 为 `~/.dsh`）下的全局补丁层 `~/.dsh/cordis.patch.yml` 被写成无法解析的 YAML（例如 `!!js` 表达式中含未加引号的 `: `：`YUNXIAO_ACCESS_TOKEN: !!js process.env.TOKEN ? process.env.TOKEN : ''`）
[测试步骤] 1. 在上述状态下启动桌面端，观察「Plugin installation」阶段的失败原因与界面提示。2. 点击错误页出现的「隔离损坏的补丁文件」按钮（或在错误页点击「安全模式」）。3. 观察 `~/.dsh` 下文件变化、应用是否重启成功与 toast 提示。4. 修复原 YAML 后把备份文件改回 `cordis.patch.yml`，重启确认恢复
[预期结果] 1. 阶段失败原因为 `INTERNAL_PLUGIN_INSTALL_FAILED: INTERNAL_PLUGIN_PATCH_PARSE_FAILED: <补丁文件路径>: <YAML 解析错误>`，界面展示 `errors.patch_layer_parse_failed` 提示（含解析器给出的位置），并额外提供「隔离损坏的补丁文件」按钮；不会静默跳过损坏层（dsh 上游契约要求显式失败）。2. 隔离动作把无法解析的层重命名为 `<原名>.broken-<UTC yyyymmddhhmmss>`（同名已存在时追加 `-2`、`-3`…），**不删除文件**；仅隔离本次启动实际组合的层（当前档案层 + 全局 `$DSH_HOME/cordis.patch.yml`）。3. 应用重启后正常进入 Running（`http://127.0.0.1:3080/healthz` 返回 200），成功隔离的每层各弹一条 `patch.quarantined_toast`（`<原路径> → <备份路径>`）；**改名失败时（文件被占用/权限不足）不切换档案、不重启**，返回 `PATCH_LAYER_QUARANTINE_FAILED: <路径>: <原因>`，界面改弹 `errors.patch_quarantine_failed` 提示用户先释放文件或手动改名。4. 用户把备份改回原名后，补丁层重新生效；再次触发隔离时因原文件已不存在而不产生任何备份文件（幂等）

## [P1] 验证 pnpm-workspace.yaml 多文档被归一化并恢复插件安装

[测试类型] 可靠性
[前置条件] `$DSH_HOME/profiles/<当前档案>/pnpm-workspace.yaml` 被手工或工具拼接成两个 YAML 文档（`packages:` 等设置后跟一行 `---` 再跟 `autoInstallPeers: false`）；pnpm 与 serde_yaml 都只接受单文档流
[测试步骤] 1. 在该状态下启动桌面端（会走插件安装前置步骤），观察日志与「Plugin installation」阶段结果。2. 打开该 `pnpm-workspace.yaml`，核对文档数量、原有键与 `minimumReleaseAgeExclude`。3. 在该档案目录执行 `pnpm config get nodeLinker`（或任何读取该文件的 pnpm 命令），确认文件已可被 pnpm 读取。4. 再把文件改成「第二份文档不是映射」（例如 `- a`）后重启，观察报错是否仍带文件路径
[预期结果] 1. 日志出现 `PROFILE_WORKSPACE_MULTI_DOCUMENT: normalized <路径> to a single YAML document`，阶段不再失败、应用正常进入 Running。2. 文件被写回为**单文档**：`parse_workspace_document` 按顺序合并各文档（同名键后者覆盖前者），原有键（`packages` / `nodeLinker` / `autoInstallPeers` 等）不丢失，并补齐 `minimumReleaseAgeExclude: - zod@4.4.3`。3. pnpm 能正常读取该文件，不再出现 `expected a single document in the stream, but found more`。4. 存在非映射文档或真正的语法错误（如 issue #49 的重复映射键）时不做带病归一化，仍返回 `PROFILE_WORKSPACE_INVALID_YAML: <文件路径>: <解析错误>`（路径便于用户定位要修哪个文件）
