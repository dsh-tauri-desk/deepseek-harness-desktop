# 桌面端自更新 — 版本检查与更新（10-updater / 01）

## [P1] 验证启动后自动检查 GitHub 是否有新版本
[测试类型] 功能
[前置条件] 已安装生产版桌面端（Windows，本机版本 0.6.5）；GitHub 上最新版本为 0.6.6；网络畅通
[测试步骤] 1. 启动生产版桌面端（端口 3080），等待进入主界面并完成初始化。2. 保持网络畅通，观察应用在启动后对 GitHub 的检查请求及版本比对结果
[预期结果] 1. 桌面端正常启动至主界面，初始化无中断、无错误弹窗。2. 应用启动后在后台自动向 https://github.com/hairyf/deepseek-harness-desktop/releases.atom 发起一次实时检查（无缓存），判定最新 tag v0.6.6 高于本机 0.6.5，确认存在新版本

## [P1] 验证发现新版本后静默下载并出现「更新可用」chip
[测试类型] 功能
[前置条件] 已安装生产版桌面端（Windows，本机版本 0.6.5）；GitHub 最新 0.6.6；网络畅通；AppData 的 updates 目录下无对应安装包
[测试步骤] 1. 启动桌面端，等待自动检查发现新版本 0.6.6。2. 观察右下角是否有提示，以及顶部导航栏「帮助」右侧是否出现 chip。3. 观察 desktop-update-progress 事件推送与 AppData/updates 目录
[预期结果] 1. 不弹出任何右下角「发现新版本」toast；更新入口是「帮助」右侧的「更新可用」chip（帮助菜单的「检查更新」项右侧仍显示「存在新版本」）。2. 安装包在后台静默下载：desktop-update-progress 事件由 0 递增到 100，所选资产为当前平台匹配项（Windows 为 Deepseek.Harness.Desktop_0.6.6_x64-setup.exe）。3. 安装包落到 AppData/updates/Deepseek.Harness.Desktop_0.6.6_x64-setup.exe，且 store 写入 desktop_pending_installer（路径 + 版本 0.6.6）

## [P1] 验证「更新可用」chip / 帮助「检查更新」打开对话框并可完成安装
[测试类型] 功能
[前置条件] 已发现 0.6.6 新版本（安装包可能仍在下载，或已下载完成）
[测试步骤] 1. 点击顶部「更新可用」chip，观察对话框内容。2. 下载仍在进行时点击「立即更新」。3. 待下载完成后重新打开对话框并点击主按钮。4. 通过「帮助 > 检查更新」重复一次
[预期结果] 1. 两个入口打开同一个「发现新版本」对话框，展示当前版本与新版本号。2. 下载中打开对话框实时显示进度条；此时点「立即更新」会等待本次下载结束、完成后自动打开安装包（不重复下载）。3. 已下载时显示「安装包已下载，可直接打开」、主按钮为「打开安装包」，点击后系统默认处理器启动安装器（Windows 触发 UAC），对话框收起并提示「已打开安装包，请按提示完成安装」。4. 下载中对话框可正常关闭（下载在后台继续），再次打开仍能看到最新进度或已下载状态

## [P2] 验证当前已是最新版时提示无需更新
[测试类型] 功能
[前置条件] 已安装生产版桌面端（Windows，本机版本与 GitHub 最新版本均为 0.6.6）；网络畅通
[测试步骤] 1. 启动桌面端（端口 3080），等待自动检查完成版本比对。2. 查看界面更新的提示与按钮状态
[预期结果] 1. 应用查询到最新 tag 为 v0.6.6 并与本机 0.6.6 比对，判定最新不高于本机，结果为无需更新。2. 界面提示「当前已是最新版本」，不出现「更新/下载」按钮，无更新弹窗

## [P3] 验证网络不可达时检查失败且不影响正常使用
[测试类型] 功能
[前置条件] 已安装生产版桌面端（Windows）；断开网络或封禁 github.com（releases.atom 与 expanded_assets 不可达）
[测试步骤] 1. 断网后启动桌面端（端口 3080），进入主界面。2. 触发检查更新（启动自动检查或点击「检查更新」），等待请求超时（5 秒）返回。3. 随后继续使用核心功能，如查看已安装核心列表、切换到指定档案
[预期结果] 1. 检查在 5 秒超时后失败，check_desktop_update 返回 UPDATE_ATOM/UPDATE_ASSETS 错误，桌面端不崩溃、不阻塞。2. 界面提示「检查更新失败」，桌面端主界面仍正常显示。3. 可继续查看核心列表、切换档案等核心功能，服务正常启动不受影响

## [P3] 验证更新下载失败不打扰用户且可重试
[测试类型] 功能
[前置条件] 已安装生产版桌面端（本机版本 0.6.5）；GitHub 最新 0.6.6，已发现新版本；封禁 github.com 与 ghfast.top 两个下载源
[测试步骤] 1. 发现新版本后进入静默下载，期间同时封禁主源 github.com 与镜像源 ghfast.top。2. 等待下载失败返回，观察界面提示与 updates 目录。3. 恢复网络后打开「更新可用」chip 的对话框，点击「立即更新」
[预期结果] 1. 下载中止，desktop-update-progress 事件停止推送，临时文件 .part 被清理，updates 目录下不残留该安装包，且后台静默失败不弹错误 toast。2. 对话框主按钮仍为「立即更新」；点击后重新发起下载，失败时提示「安装包下载失败」（含已尝试 2 个下载源信息），应用不崩溃、不死循环。3. 恢复网络后重试，进度从 0 重新开始直至 100%，最终在 updates 目录生成安装包

## [P1] 验证关闭应用后自动打开已下载的更新程序
[测试类型] 功能
[前置条件] 已安装生产版桌面端（Windows，本机版本 0.6.5）；已静默下载 0.6.6 安装包，且未在对话框内点击过「打开安装包」
[测试步骤] 1. 通过托盘菜单「退出」关闭应用（或在设置中把关闭按钮行为设为「退出应用」后点击关闭按钮）。2. 观察系统是否自动打开安装器。3. 重新下载 0.6.6 后先在对话框点击「打开安装包」，再退出应用
[预期结果] 1. 应用退出后系统默认处理器自动打开 AppData/updates 下的 0.6.6 安装器（Windows 触发 UAC）。2. 版本护栏生效：仅当待安装版本严格高于当前运行版本才自动打开，否则跳过并写日志（防止用户已用别的方式升级后被降级安装）。3. 已在应用内打开过安装包（store 中 desktop_pending_installer 已清除）时，退出不再重复拉起安装器

## [P2] 验证开发版与生产版使用彼此隔离的更新/数据
[测试类型] 兼容性
[前置条件] 同时存在 debug 构建（pnpm tauri dev）与生产构建，且两个构建均可正常运行
[测试步骤] 1. 同时启动 debug 构建（端口 3081）与生产构建（端口 3080），并保持运行。2. 分别检查两个构建使用的端口、$DSH_HOME、store 文件与服务日志。3. 对生产版执行一次桌面端自更新（检查并下载安装包）后重启，再次查看 $DSH_HOME 与 store 文件
[预期结果] 1. debug 构建使用端口 3081、$DSH_HOME 为 ~/.dsh.dev、store 文件 .store.dev.dat、日志 logs/dsh-web.dev.log；生产构建使用端口 3080、$DSH_HOME 为 ~/.dsh、store 文件 .store.dat、日志 logs/dsh-web.log，两者互不污染。2. 两端口可同时监听不冲突，debug 构建通过 ~/.dsh.dev/.harness.pid 精确回收自有服务进程，不会终止生产版服务。3. 桌面端自更新仅替换桌面壳，更新前后 $DSH_HOME 与 .store.dat（核心数据）内容保持不变，共用内核未受影响
