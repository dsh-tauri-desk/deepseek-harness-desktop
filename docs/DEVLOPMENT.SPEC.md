根据您的要求，从该规范评审与实战手册中抽离出的通用软件开发协议如下：

# 通用软件开发规范与协议 (Universal Software Engineering Protocol)

---

## 一、 基本架构与演进原则 (Core Principles)

1. **唯一事实来源 (Single Source of Truth, SSOT)**
  * **原理**：系统中任意一份数据或状态只能存在唯一的 authoritative 来源。
  * **规则**：严禁创建“顺手的副本”或重复的本地状态。多处读取时，仅允许由单点发起写/更新逻辑，其余消费者一律通过 Read-Only/订阅机制使用该数据。
  * **推论**：重构的硬性目标是将状态修改与删除的复杂度控制在 $O(1)$，而非 $O(N_\text{引用点})$。
2. **零无用中间层 (Zero Pass-Through Layers)**
  * **原理**：防止过度抽象，拥抱内联（Inline-First）。
  * **规则**：若一个 Hook、组件、函数、工具文件（Util）仅有一个消费者/调用方，**严禁**为其单独建立独立文件或封装中间层，应直接内联至消费者中。
3. **事故驱动规范 (Incident-Driven Protocols)**
  * **原理**：架构规范不应只是代码风格规范，更是历史故障的防御机制。
  * **规则**：非显而易见的边缘处理逻辑或平台兼容性代码，必须附带事故追踪标识（如 `issue #xxx`）或具体的平台机制说明（写明 *Why* 而非 *What*）。
4. **渐进式激进重构 (Radical Cleanup without Legacy)**
  * **原理**：保持代码库的清爽度，杜绝长期存活的兼容过渡层。
  * **规则**：重构时优先进行彻底删除与直接替换，禁止保留带有 `_legacy`、`_old` 或无引用的兼容层文件。重构过程应优先使用版本控制系统的原生移动/重命名命令（如 `git mv`）以保留完整的历史上下文。

## 二、 响应式与副作用管理协议 (Reactive & Side-Effect Protocol)

1. **声明式副作用优先 (Declarative Effects)**
  * **原理**：将“什么时候执行”的时序控制转换为“数据依赖”的响应式映射，消除隐式时序与竞态风险。
  * **规则**：
  * 值的变更监听、挂载执行、事件订阅、DOM/系统偏好观察等，必须统一抽象为专用的声明式 API/Hooks。
  * 禁止在组件内到处散落原生命令式副作用（如裸写 `useEffect` / `watch`）。
2. **命令式副作用白名单制 (Explicit Escape Hatches)**
  * **原理**：显式化复杂的生命周期与资源清理逻辑。
  * **规则**：仅在需要显式注册与销毁**外部资源**（如 Native 窗口生命周期、取消在途网络请求、初始化复杂第三方无 SDK 实例）时，才允许使用原生命令式副作用，且必须使用特定注释标记例外原因（例如：`// keep:effect <原因>`）。
3. **外部事件消费模式**
  * **规则**：跨组件或跨进程的瞬时事件消费，必须通过统一注册的事件总线（Event Bus）或集中式声明挂载点进行收口，避免在业务深层独立监听。

---

## 三、 模块与目录分类协议 (Directory Layout Protocol)

所有代码的物理落点必须严格由“依赖关系”与“业务语义”确定，遵循以下决策树：

```
代码/逻辑判定标准
├─ 1. 只被单一状态模块/Store 使用？
│   └─ 归属于该 Store 模块目录下 (不放入全局)
├─ 2. 纯 UI 表达，无业务语义，只依赖基础 UI 库或纯工具函数？
│   └─ 归属于 components/ (通用组件库)
├─ 3. 依赖了具体业务状态 (Store)、系统 API、或业务领域数据？
│   └─ 归属于 ui/<特定业务领域>/ (业务 UI)
├─ 4. 无状态、无 UI、跨模块复用的纯逻辑计算？
│   └─ 归属于 utils/ (全局工具库)
└─ 5. 可复用的组件状态/行为逻辑？
    └─ 归属于 hooks/

```

* **文件归宿收敛**：`utils/` 目录严禁作为“杂货铺”，仅允许存放纯函数与全局单例（如 Logger、Clipboard 工具）。

---

## 四、 跨边界通信协议 (Boundary & IPC Protocol)

1. **通信协议白名单**
  * 宿主环境与上下文（如 Host 与 Iframe/Plugin/Native）之间通信，必须基于显式定义的白名单 API 原语与规范化数据结构（如 `{ type, payload }`）。
2. **校验与分发分离**
  * 来源与安全性校验（Origin Check）必须在通信原语入口处统一处理**一次**；具体业务协议分发仅依据数据报文的类型（如 `type`）进行，禁止在分支逻辑中重复比对通信来源。
3. **让位原则与细粒度标记 (Granular Capability Delegation)**
  * 当底层系统 shim/注入脚本与高层插件/应用同时存在时，让位标记（Bridge Override）的语义必须精确到**具体命令/事件粒度**，严禁使用全局“一键停用”开关，防止部分接管导致其他系统能力静默失效。
4. **归属判定**
  * 优先将业务能力放置在离高层 API 最近的一侧；仅当需要抢占脚本执行时机（如 API Mocking、Boot 异常捕获、DOM 捕获阶段拦截）时，才允许保留底层 Shim 或注入脚本 。

---

## 五、 状态持久化与平台兼容协议 (State & Platform Protocol)

1. **写缓存与读取解耦**
  * 多个消费者读取同一数据时，仅由唯一明确的入口（如根布局或数据同步服务）负责将外部事件写入缓存；其他消费者仅允许进行只读订阅。
2. **持久化 hydration 同步原则**
  * 在涉及跨语言/进程（如 Node/Browser 与 Rust/C++）共享持久化数据结构时，**共享 Key 的写回必须发生在完整的 Hydration（反序列化初始化）之后**，防止使用局部初始状态覆盖持久化全量数据。
3. **双端校验机制 (Dual-Side Normalization)**
  * 数据边界的处理（如数值范围约束、格式归一化）必须在**写入侧（前端/应用层）进行第一次归一化**，并在**读取侧（后端/Native 侧）进行兜底校验**。
4. **前置平台能力判定**
  * 针对跨平台或不同系统版本的限制，能力不支持的平台必须在**调用发起前**通过同步的能力/系统版本判定拦截，禁止依赖调用失败后的捕获/回退机制。

---

## 六、 提示与副作用出处协议 (UI Feedback Protocol)

1. **用户提示单出处**
  * 遵循“**谁执行，谁提示**”原则。用户操作产生的反馈提示（如 Toast、Alert）只能由底层具体的执行函数发出，禁止在层层调用的上层各写一遍成功/失败提示。
2. **组件复合导出**
  * 强相关的域组件或微小零件组件，应优先使用复合组件形式导出（例如 `Panel.Header` / `Panel.Content`），避免为简单的样式/结构零件碎片化创建独立文件。

---

## 七、 质量交付与工程自检协议 (Quality & Verification Protocol)

在任何功能开发或重构交付前，必须按照以下 **6 步决策检查列表** 完成自检：

* [ ] **真值校验**：该事实/状态是否拥有唯一真值？是否存在第二份副本？
* [ ] **消费收敛**：是否存在只有一个消费者的中间层/Hook/Util？（若有，强制内联）。
* [ ] **目录对位**：代码落点是否严格符合 `components/` vs `ui/<领域>/` vs `store/` 的判定标准？
* [ ] **副作用审查**：副作用是否已最大程度声明式化？原生副作用是否加上了 `// keep:effect` 标记及注释？
* [ ] **符号残留与通信检查**：重命名或废弃原语后，是否已通过全局 Grep 确认旧符号零残留？通信修改是否导致未定义异常？
* [ ] **构建与类型验证**：类型检查（Typecheck）、Lint 规则、静态 Import 解析校验、自动化测试与 Native 编译是否全部通过？
